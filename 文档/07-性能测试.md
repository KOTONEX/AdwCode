# 性能测试

本文记录 2026-10-06 的本机性能测量，用于后续回归比较。历史测试版本为 2.0.0，
初次测量的产品代码基线为 `2abc4a6`，脚本记录于 `c36fdb5`。前文保留该历史结果；
文末另记录性能修复后的配对对照，当前基准的状态同步方法已有更新。

## 环境与方法

- Intel Core Ultra 7 255H，系统报告的 `MemTotal` 约为 31 GiB。
- Linux 7.2.6-ogc1，Python 3.14.8 自由线程版本，GIL 关闭；Node.js 26.10.0。
- VS Code 1.140.0，Chromium 150.0.7871.250；沿用系统显示缩放，比较在同一窗口进行。
- 命令行在临时副本中执行，每项预热 2 次，测量 20 次；文件缓存不清空。
  P95 使用最近秩，即第 `ceil(0.95*n)` 个有序样本。
- 界面使用独立用户数据、扩展目录与工作区，只有本项目及 VS Code 内建扩展。
  自动重载关闭，小地图、固定滚动标题与编辑器平滑滚动关闭。
- 测试文件包含 6000 行 Python 代码，工作区有 200 个额外文件；压力场景再添加
  1000 个非虚拟侧栏行。实际工作台的节点数量约为 1300～1400，压力场景约为 3400。
- 比较同一套主题与产品图标下的原生 CSS 和附加 CSS，顺序交替，
  每个场景每种样式预热 1 次、测量 6 次。明暗与三个场景共 72 个有效样本。
  非活动规则的单独对照另有 36 个样本。

## 开发命令

耗时包括解释器启动和实际工作；RSS 是 exec 后以 0.5 ms 间隔观测到的内存
高水位，短进程可能漏掉最后的峰值。此处只统计被测单进程，不是 VS Code 总内存。

| 操作 | 中位耗时 | P95 | 观测峰值 RSS |
| --- | ---: | ---: | ---: |
| Python 空进程 | 10.43 ms | 11.26 ms | 12.7 MiB |
| 默认构建（10 个主题，不读取系统） | 61.06 ms | 63.66 ms | 28.6 MiB |
| 默认主题校验 | 55.66 ms | 56.62 ms | 25.8 MiB |
| CSS 兼容校验 | 210.29 ms | 213.77 ms | 97.3 MiB |
| VSIX 打包 | 76.55 ms | 77.65 ms | 28.6 MiB |

默认构建低于 0.1 秒的中位耗时，本次未发现生成器或打包的明显
等待瓶颈。CSS 兼容校验会扫描已安装的工作台 CSS 与 JavaScript，耗时和内存较高；
它只在开发检查时运行，不属于日常编辑过程。

## 外观 CSS

表中数值为每个操作分摊的渲染器任务时间中位数。非活动场景每个样本强制切换
并刷新样式 200 次；滚动场景每个样本通过 CDP 发送 50 次实际滚轮输入，并验证
可见内容确实变化。滚动的协议等待不计为 CPU 时间，但自动化输入和采样脚本仍
可能影响渲染器任务计时，因此用配对结果判断差异。

| 场景 | 浅色：原生 / 附加 CSS | 深色：原生 / 附加 CSS |
| --- | ---: | ---: |
| 工作台非活动状态切换 | 0.655 / 3.530 ms | 0.609 / 3.543 ms |
| 编辑器滚动 | 9.119 / 8.616 ms | 9.874 / 10.593 ms |
| 1000 行侧栏压力 | 0.606 / 3.592 ms | 0.609 / 3.595 ms |

滚动任务时间在浅色下稍低、深色下稍高，差异方向不一致；不足以据此判定附加 CSS
会稳定加速或拖慢滚动。原始 `frames` 数组是串行 CDP 输入后的 RAF 采样间隔，
不是独立的应用帧时间，不能用它计算 FPS 或掉帧率。本轮未测量 GPU 绘制和长时内存变化。

非活动状态切换增加了约 3 ms 的单次任务开销。进一步临时剔除包含 `:has()` 的
非活动样式整组规则，结果如下：

| 样式 | 浅色每次任务 | 深色每次任务 |
| --- | ---: | ---: |
| 原生 CSS | 0.630 ms | 0.606 ms |
| 完整附加 CSS | 3.514 ms | 3.522 ms |
| 剔除非活动规则 | 0.641 ms | 0.634 ms |

额外开销主要来自非活动样式这一组规则及其触发的状态更新，而非所有 CSS。
剔除整组规则也取消了对应的视觉变化，本实验没有区分选择器匹配和属性更新的成本，
不能保证仅改写 `:has()` 语法就能获得同样收益。它可以作为后续缩小状态更新范围的依据。
本轮仅测量，不以取消该视觉功能作为优化结果。

## 初次测量时的加载配置

测试窗口从 VS Code 安装目录中读取到了 5 段项目样式：两份 `GNOME外观.css`、
两份窗口控件 CSS 和一份字体 CSS。另只读核对了操作者的加载器配置，确认其同时
引用了仓库源文件与安装副本，两个同名组件重复加载；两份外观样式的内容长度也不同。

重复引用既可能增加样式处理，也可能让已删除的旧规则继续生效。
上述数据先从测试 DOM 中移除全部已注入项目样式，再注入当前三个 CSS 文件一次，
因此测量的是当前源码的开销，不包含重复配置。清理加载器引用后，应先同步安装
副本，再在工作结束后手动加载；本次没有修改操作者配置、磁盘补丁或重载工作窗口。

## 性能问题修复与复测

外观安装命令现在将本次组件在扩展源目录及安装目录中的引用统一为单份副本，
保留其他用户加载项与顺序；状态面板报告重复配置和重复注入。其他克隆目录、
占位符 URI 尚未自动识别，不按文件名删除未知来源。

非活动状态改由 `窗口状态.js` 观察原生标题栏，并只在导航容器同步状态类。
普通 CSS 选择器保留原有标签配色及工具栏透明度，避免工作台祖先的关系匹配。
脚本不轮询，活动时不观察布局；非活动时忽略正文与列表内容的 DOM 变化，
仅处理布局新建导航区域。重复注入和页面关闭会释放观察器。

在同一独立窗口中比较原生 CSS、修复前 CSS 与当前 CSS，交替各测量 6 次。
全部场景共 108 个有效样本。各组都运行状态脚本，每次切换后等待一个微任务，
确保观察器已同步；因此以下数据只在本轮内部比较，不与前文的同步循环直接相减。

| 场景与模式 | 原生 | 修复前 | 修复后 |
| --- | ---: | ---: | ---: |
| 非活动状态切换，浅色 | 0.781 ms | 3.654 ms | 1.904 ms |
| 非活动状态切换，深色 | 0.779 ms | 3.759 ms | 1.908 ms |
| 1000 行侧栏压力，浅色 | 0.861 ms | 3.875 ms | 1.982 ms |
| 1000 行侧栏压力，深色 | 0.857 ms | 3.863 ms | 1.977 ms |

非活动切换的总任务时间降低约 48%～49%，相对本轮原生的额外开销降低约
61%～62%。当前仍有约 1.1 ms 的额外工作，并不等同于取消视觉变化后的原生开销。

浅深色下各对照 20 个导航与标签元素的活动、非活动计算样式，颜色、背景和透明度
与修复前一致；编辑器正文颜色保持不变。新增标签和导航区域、重复脚本注入、
恢复活动状态及高对比度类保护通过实际工作台断言。
这些断言不是完整高对比度主题的截图验收，也不代表日常插件组合已完成试用。

滚动再以每种样式、每种模式 8 次独立复核，共 48 个有效样本。每轮重新定位并
聚焦可见编辑器，断言输入位置和可见内容变化；未实际滚动的中断结果不入库。
启动阶段等待 DOM 以及观察器释放检查也通过。

| 滚动样本 | 原生 | 修复前 CSS | 修复后 CSS |
| --- | ---: | ---: | ---: |
| 完整对照，浅色 | 8.624 ms | 10.874 ms | 9.990 ms |
| 完整对照，深色 | 7.786 ms | 8.517 ms | 9.436 ms |
| 单独复核，浅色 | 9.711 ms | 9.055 ms | 9.954 ms |
| 单独复核，深色 | 8.988 ms | 8.299 ms | 7.888 ms |

修复前后 CSS 的滚动差异在两轮中反向，没有稳定趋势，不宣称获得滚动加速，
也不依据这些采样间隔给出 FPS。详见
[单独滚动复核](资产/性能数据/2026-10-06-fixed-scroll.json)。

复测期间，测试主机的加载路径已统一为三份 CSS 副本及一份状态脚本，并保留
原配置备份。该记录反映当时的测试环境，不代表其他安装已自动更新。实际安装和
手动加载步骤见 [开发、验证与发布](04-开发验证与发布.md#手动预览)。

修复对照的复现方式见源码仓库的 `基准/README.md`。
