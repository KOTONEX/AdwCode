# 版本控制

日常使用最新稳定版 Jujutsu（`jj`），与 Git 共置：仓库根目录同时保留 `.jj/` 和
`.git/`。历史、提交 ID、`主线` 和已有版本标签保持可供 GitHub 使用；CI 无需安装 jj。
`.jj/` 保存本地工作副本和操作记录，不提交、不进入 VSIX。

共置模式会自动同步 jj 书签与 Git 引用；Git 的 detached HEAD 是正常状态。
不要为了恢复“当前分支”执行 `git switch`，也不要混用 Git 暂存区整理 jj 变更。
预览使用 Git 读取目标提交和本地标签；完整历史仅用于日志与发布。打包文件清单在共置仓库中
改读 jj 跟踪状态，能包含已 `jj file track`、尚未进入 Git 索引的新文件。

## 初始化与身份

已有完整 Git 仓库，在根目录运行一次：

```sh
jj git init --colocate --config 'snapshot.auto-track="none()"'
jj config set --repo snapshot.auto-track 'none()'
jj bookmark track 主线@origin
```

从 GitHub 新建本地副本则使用以下入口，再执行相同的仓库级配置：

```sh
jj git clone --colocate --config 'snapshot.auto-track="none()"' https://github.com/KOTONEX/AdwCode.git AdwCode
cd AdwCode
jj config set --repo snapshot.auto-track 'none()'
```

Jujutsu 不会自动沿用 Git 的作者身份。先查看 `jj config list user`，按本机已有署名、
仓库 Git 配置或 gh 账号核实真实姓名与邮箱，再通过 `jj config set --repo user.name`
及 `jj config set --repo user.email` 分别设置。仅在刚初始化且工作副本作者为空时，
运行 `jj metaedit --update-author -r @` 更新自己的工作副本作者，不改写他人的历史。
上述配置仅影响本仓库，不改全局身份。

初始化会识别主线；本仓库的 `trunk()` 指向 `"主线"@origin`，用 `jj config list --repo`
核对。若未识别，可设置 `jj config set --repo 'revset-aliases."trunk()"' '"主线"@origin'`。
首次迁移后的 `主线` 与 `主线@origin` 继续指向迁移前的已发布提交。

## 跟踪与完成变更

```sh
jj status
jj diff --summary
jj diff
jj log
```

`@` 是当前工作副本变更，`@-` 是其父提交。jj 会自动快照已跟踪文件，因此 `jj status`
本身也可能更新本地工作副本提交 ID；这不表示已完成项目提交、移动主线或上传 GitHub。
不要把每次自动快照当成需要重新打包安装的交付提交。

本仓库关闭新文件自动跟踪，避免调试日志、临时源码等被自动收录。新增文件必须明确指定：

```sh
jj file track 文档/开发/版本控制.md
jj diff --summary
cargo 检查
```

参数采用 jj 的 fileset 语法。路径含括号等特殊字符时，使用精确匹配和两层引号，
例如 `jj file track 'file:"文档/开发/示例(一).md"'`，避免被解释为模式或表达式。

该配置不会屏蔽已跟踪文件的本地改动。例如 `.vscode/settings.json` 仍显示在 `@`，
但私有修改应留在本地。完成变更时传入本次路径，而不是对整个工作副本直接设置主线书签。
以下仅示范选择两个文档路径，实际按本次任务调整：

```sh
jj commit -m "文档: 完善开发说明" README.md 文档/开发/版本控制.md
jj show -r @- --summary
```

选定路径进入已完成提交，其他修改留在新的 `@`；仔细核对 `@-` 的描述、文件与补丁。
涉及 VSIX 实质产物变化时，按 [AGENTS.md](../../AGENTS.md#提交) 运行 `cargo 预览`，
打包 `@-` 并打开安装了该提交扩展的全新窗口。未带匹配版本标签时使用独立环境，
只有 `@-` 本身带有与清单匹配的 `v<版本>` 标签时才安装到日常用户环境，不重载原有窗口。
纯文档更新及其他不改变 VSIX 实质产物的提交跳过自动安装和预览；文档随包收录、
自动变更日志或归档元数据的变化不单独触发。
`jj log -r @- --no-graph -T commit_id` 给出隔离检出所用的 Git 提交 ID。
自动变更日志读取已完成的 Git 历史，不包含 `@` 的未完成描述与工作副本修改。

## 主线与同步

```sh
jj git fetch --remote origin
jj bookmark list 主线
jj log -r '主线 | 主线@origin | @ | @-'
```

获取远端不会把当前工作副本自动搬到主线。远端有新提交时，先核对历史与变更范围，
再决定如何 rebase；不要将含有无关修改的整个本地变更链直接推送。

仅在已授权推送、`@-` 确认只含本次任务且适用的检查和安装预览完成后：

```sh
jj bookmark set 主线 -r @-
jj git push --remote origin --bookmark 主线 --dry-run
jj git push --remote origin --bookmark 主线
```

书签位置需要显式更新，`jj commit` 不会自动移动它。推送只指定本次书签，避免使用
`--all`。没有推送授权时，保留本地变更与现有远端状态。

## 标签与发布边界

已有标签和正式发布不可移动。jj 可创建轻量标签，但当前不创建附注标签；本项目继续
通过 Git 兼容层创建附注版本标签，再用 jj 推送。下列是发布模板，`<版本>` 必须替换为
`package.json` 的版本，`<提交ID>` 必须是已经完成、检查、安装且推送到主线的目标：

```sh
git tag -a "v<版本>" "<提交ID>" -m "发布<版本>：具体变化"
jj git push --remote origin --tag "v<版本>" --dry-run
jj git push --remote origin --tag "v<版本>"
```

先核对 `git rev-parse HEAD`、目标提交 ID、`主线` 书签与远端主线一致；工作副本应是
该提交的直接后继。发布打包和上传从目标提交的干净完整历史副本运行，以免本地用户
改动影响上传校验。只有明确的标签／发布授权才执行这些操作，主线推送不等于 Release。
CI、正式／候选判断和市场令牌规则继续见 [发布](发布.md)。

Jujutsu 的操作记录使用 `jj op log` 检查；需要回退时先确认具体操作，不把 `jj undo`
当作工作区清理命令，也不假定它可以撤回已经推送的标签或外部发布。

官方参考：[Git 共置与标签支持](https://docs.jj-vcs.dev/latest/git-compatibility/)、
[跟踪设置](https://docs.jj-vcs.dev/latest/config/#paths-to-automatically-track)。
