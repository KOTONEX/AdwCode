# 发布

本文说明当前版本、提交、CI 与发布流程。环境和检查命令见 [开发验证](开发验证.md)。

## 提交与发布

VSIX 产物不变的改动只提交与推送，不更新发布版本号、不打版本标签、不创建 Release。
是否发布以实际打包内容的变化为依据，不因产生新提交而自动发布。

1. 明确本次提交范围，按路径暂存，排除调试日志、构建产物及无关改动。检查暂存差异及 `git diff --cached --check`。
2. 使用 [贡献规范](../../CONTRIBUTING.md) 的中文类型前缀，描述最终实际行为。
   正文可列修改原因与验证结果，避免只有“准备发布”等过程性描述。
3. 本机 Git 身份缺失时核对 gh 账号和已有作者信息；必要时询问，不伪造邮箱。
   临时身份可通过 `git -c user.name=… -c user.email=… commit` 指定。
4. 版本只修改 `package.json`；提交后通过 `cargo run --quiet -- 变更日志` 从 Git
   历史生成日志，不手工维护版本章节。更新版本不等于
   已公开发布，提交也不等于已推送。
5. 打包检查 VSIX 的版本、主题清单和归档完整性；`[Content_Types].xml` 中的
   扩展名不带前导点，CSS 类型为 `text/css`。VSIX 不提交到仓库。
6. 确认发布范围与权限后推送对应 `v<版本>` 标签，触发发布工作流。标签提交尚未进入
   `main` 或版本号带预发布部分时，Release 标为候选，不更新 latest，也不发布市场。
   CI 同时检查 `main` 与 `rust`；重新生成主题和全部字体必须与受跟踪产物一致。
   正式市场发布要求标签版本一致、提交已进入 `main` 且版本不带预发布部分；还需要
   `VSCE_PAT`、`OVSX_PAT`，缺失时工作流跳过对应市场，不宣称市场已经发布。
   同一引用的发布任务串行执行；重跑时保留已有 Release 和同名 VSIX，只补齐缺失附件
   并更新说明，市场发布复用已公开的 VSIX。不要移动已发布的版本标签；确需修正
   附件时，应单独确认替换范围。

文档记录稳定流程；提交状态、环境配置和发布结果以实际检查为准。
公共文档中的相对链接必须指向随仓库提交的文件。

每次创建或修订提交后，按 [AGENTS.md 的提交规范](../../AGENTS.md#提交)，从完整历史的
隔离副本生成主题及 VSIX，安装绝对路径的包并核对版本，再清理副本。此本机安装
不会重载当前窗口，也不自动授予推送、标签或 Release 权限。

提交、推送、标签、GitHub Release 和各市场发布分别记录状态；版本更新或 main 推送
不会自动创建 Release。文档随 VSIX 分发，文档调整可能改变包内容；未授权公开发布时
仍只提交、推送并完成本机验收，不擅自增加版本或创建标签。

## CI 工具复用

成功的 main／rust push CI 保存同提交的 Linux x64 release 工具及元数据，保留 30 天。
标签发布只接受本仓库 ci.yml 的同 SHA 成功 push、唯一且未过期的产物，校验提交、
平台与 SHA-256 后复用。没有可用产物时安装 Rust 并执行完整检查和 release 构建；
API、下载或摘要校验错误直接失败，不以备用构建掩盖错误。

复用只省去重复 Rust 构建，Node.js 与 TypeScript 仍准备最新稳定版。标签上重新生成
资产、严格编译脚本并打包，以保留标签变更日志的语义。相关工作流见
[ci.yml](../../.github/workflows/ci.yml) 与 [release.yml](../../.github/workflows/release.yml)。

## 本地与 CI 共用上传

完成完整检查、提交和版本标签校验后，打包与上传使用相同入口：

```sh
git fetch origin main --tags
cargo build --release
./target/release/adwcode 打包
./target/release/adwcode 发布上传 --引用 refs/tags/v<版本> --目标 Release --预演
./target/release/adwcode 发布上传 --引用 refs/tags/v<版本> --目标 Release
```

`--预演` 不访问发布服务，只校验完整历史、标签与 HEAD/清单一致、打包源文件
无未提交修改及 VSIX 内容。先重新打包，避免把未打标签时的变更日志上传。
上传使用清单中的 GitHub 仓库，需已认证的 `gh`（CI 使用 `GH_TOKEN`）。
上传命令假定完整检查已成功，不代替完整检查；本地发布仍须获得操作者授权。

已有 Release 只补齐缺少的附件并更新说明；已有同名附件下载到临时目录，
与当前标签打包内容一致才复用，内容不同直接失败，保留公开附件。
只有 HTTP 404 允许创建 Release，其他网络/认证错误直接失败。
非主线或预发布版本固定为候选 Release，不设为最新，也不允许市场上传。

正式版本在主线可达时，可复用相同 VSIX：

```sh
./target/release/adwcode 发布上传 --引用 refs/tags/v<版本> --目标 市场
```

需 `npx` 与 `VSCE_PAT` / `OVSX_PAT` 环境变量；缺少任一令牌时仅跳过对应市场。
外部工具原生读取令牌，不将令牌写入参数、文件或日志。VS Code 市场沿用
`--skip-duplicate`；Open VSX 仅在明确不存在时上传，查询失败直接中止。
同版本中途失败后可以重试，命令不会回滚已成功的远端上传。
令牌环境变量是外部工具支持的接口，见
[vsce](https://github.com/microsoft/vscode-vsce) 与
[Open VSX CLI](https://github.com/eclipse-openvsx/openvsx/blob/main/cli/README.md)。

## 自动变更日志

仓库不维护手写的 `CHANGELOG.md`。完整 Git 历史、提交标题与版本标签是唯一输入；
已发布记录见 [GitHub 发布页](https://github.com/KOTONEX/AdwCode/releases)。

```sh
cargo run --quiet -- 变更日志
cargo run --quiet -- 发布说明
```

第一条生成 `builddir/CHANGELOG.md`，第二条生成 `builddir/release-notes.md`。
两者均是忽略的构建产物，不入库；可通过 `--输出` 指定输出位置。
提交标题按 `新增`、`修复`、`文档`、`测试`、`重构`、`杂务`、`初始化` 分组，
未分类的旧标题归入“其他”。日志不包含提交正文和未提交修改；正式记录需要先提交。

主线可达的 `v<版本>` 标签作为发布边界，按主线提交顺序排列；版本日期使用标签
所指提交的日期。每个范围包含合入主线的非合并提交，合并提交自身不重复列出。
不在当前主线上的标签不参与划分，首个版本包含此前全部提交，最近标签之后的
提交归入“未发布”。同一提交有多个版本标签时失败，避免发布范围产生歧义。

发布工作流执行 `./target/release/adwcode 发布说明 --标签 "$GITHUB_REF_NAME"`，必须同时
满足标签存在、指向 HEAD 且与 `package.json` 版本一致。无标签的本地说明明确标为
预览，不能作为发布校验通过的证据。浅克隆会失败；克隆时获取完整历史和标签，
CI 与发布使用 `fetch-depth: 0`，不在检查时自动访问网络补齐历史。

普通打包自动从 Git 生成 `扩展/CHANGELOG.md` 并写入 VSIX，无需先运行日志
目标。无 Git 的源码导出副本须显式传入先前生成的日志：

```sh
./target/release/adwcode 打包 --变更日志 /路径/CHANGELOG.md
```

性能基准在计时前生成固定日志，临时源码副本的打包使用该日志，不复制 Git 仓库，
也不把生成历史日志的耗时计入 VSIX 打包测量。

## 发布命令超时与诊断

GitHub 查询限时 60 秒，Release/附件操作 180 秒，市场命令 600 秒。超时会清理本次
独立进程组并返回失败；错误包含阶段与退出码，GH_TOKEN、GITHUB_TOKEN、VSCE_PAT、OVSX_PAT
在 stderr 诊断中遮蔽。工具输出保存在临时文件并有读取上限，完成后清理。
网络失败后可重新执行同一发布命令，已有附件继续逐字节核验；远端已经成功的步骤保留。

## 宿主 CI 触发与缓存

相关模块变化、每周首次 CI、官方稳定版本更新以及手动触发都会运行独立宿主。
纯版本号、颜色、字体、摘要及文档变化在本周最新版已验收时跳过宿主；完整检查和
资产校验始终执行。编辑器使用精确版本缓存，周记录只在真实测试成功后写入。
无提交时用 `gh workflow run ci.yml --ref main` 手动验证主线与最新版编辑器；
验证其他开发分支时替换 `--ref`。

CI 已编译工具后的辅助步骤统一为 `adwcode 持续集成 <步骤>`：
`宿主改动`、`宿主版本`、`宿主计划`、`宿主成功`、`登记工具`。这些命令读取
GitHub Actions 的事件、输出文件与临时目录环境；宿主计划另外读取步骤环境 `相关`、`已验收`。
宿主基线未知时保守运行，手动触发强制运行。清单只改版本或字段排序不触发宿主；
其他清单改动仍触发。登记工具读取当前运行的 release 二进制，记录提交、平台和 SHA-256。
Release 查找产物和校验工具时尚不能运行该工具，因此启动阶段保留 Python，
不额外编译来执行校验。
