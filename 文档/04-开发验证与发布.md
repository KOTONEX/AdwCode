# 开发、验证与发布

## 开始工作

先阅读 [AGENTS.md](../AGENTS.md)，查看 `git status --short` 与本次任务涉及的
差异。保留与本次任务无关的修改和未跟踪文件，避免未经确认的工作区清理。
任务涉及发布时读取 `package.json`、Git 标签与提交历史，以及发布工作流。

修改受监视文件前检查自动重载设置，避免意外中断扩展会话或调试任务。
离线测试使用模拟对象；需要界面验证时使用独立测试窗口，或由操作者手动预览。

## VS Code 工作区配置

源码仓库的 `.vscode/settings.json` 提供开发与外观试用配置，仅在打开本仓库时
生效：默认采用 `${userHome}/.local/bin/python3.14t`，对应 uv 的默认解释器安装
目录，由 ty 提供 Python 语言服务与工作区诊断。默认解释器使用完整路径，避免
环境扩展无法解析裸命令名。Python 静态检查及格式化沿用 `ruff.toml`，JavaScript
类型检查沿用 `tsconfig.json`，推荐扩展记录在
`.vscode/extensions.json`。
已有 Python 解释器选择不会因修改默认路径而切换，需要执行
“Python: Select Interpreter”选择自由线程解释器；安装目录不同时，输入实际路径。

外观预览随系统明暗模式选择 AdwCode：浅色采用彩色状态栏变体，深色采用普通变体，
高对比度的两个首选主题沿用原方案；开启命令中心，并采用 AdwCode 产品图标。
字体沿用用户设置；缩进和第三方资产的保存例外由 `.editorconfig` 与 EditorConfig 扩展管理。

工作区明确关闭 `adwcode.自动重载`，也关闭 Meson 的打开时自动配置。
`mesonbuild.buildFolder` 沿用默认的 `builddir`，修改该配置会触发 Meson 扩展的
窗口重载，因此不写入共享文件。菜单位置、标题栏和原生窗口控件等应用级配置
在用户设置中维护；工作区配置不会替代 CSS 的安装与手动加载。

本项目的开发语言是 Python 与 JavaScript，Meson 编排运行目标，不提供 C/C++
编译单元。共享配置不指定 `C_Cpp.default.*`，也不推荐 C/C++ 扩展；
`builddir/compile_commands.json` 中的 Ninja 任务不能作为 C/C++ 的编译配置。

扩展的“应用推荐设置”写入用户级外观与布局，和工作区共享同一组主题、产品图标
及布局值；它另行配置应用级窗口控件与 GNOME 代码字体，保留工作区的开发配置。
用户级与本仓库工作区的自动重载均默认关闭；恢复命令会还原备份中的用户值。

设置作用域见 [VS Code 说明](https://code.visualstudio.com/docs/configure/settings)，
ty 与 Python 语言服务的配合见 [ty 编辑器集成](https://docs.astral.sh/ty/editors/)。

## 按改动类型验证

| 改动 | 必做验证 | 额外核对 |
| --- | --- | --- |
| 配色、语法映射 | `meson compile -C builddir 主题`，完整检查 | 源修改与生成 JSON 一起提交；颜色键合法、对比度合理 |
| CSS 外观 | 完整检查，`python3.14t 源码/检查样式.py` | 类名检查只是初筛；视觉、裁切和焦点需单独验证 |
| 窗口状态脚本 | 完整检查，独立工作台基准 | 对照非活动视觉、正文、高对比度保护、新增导航与观察器释放；不重载工作窗口 |
| 扩展行为 | 完整检查 | API 类型声明、配置默认值、命令清单和错误路径同步 |
| 扩展图标 | PNG、来源记录与设计说明同步，完整检查并打包 | 参考 `资产/README.md`；保留实际源文件，核对清单、README 与 VSIX 图标资源；候选稿不随包分发 |
| 文档与提示 | 完整检查 | 简体中文、路径和命令准确，不引用未提交的文件 |
| 发布与打包 | 构建、完整检查、`meson compile -C builddir 打包` | 版本一致，产物齐全，不包含私人待办或调试日志；公共候选清单明确区分实现状态 |

使用 `uv python install 3.14t` 安装自由线程解释器，首次运行 `meson setup builddir`
配置构建目录。默认查找 `python3.14t`，也可用
`meson setup builddir -Dpython=/绝对路径/python3.14t` 指定。已有构建目录使用
`meson setup --reconfigure builddir -Dpython=/绝对路径/python3.14t` 切换。
Meson 会检查自由线程构建标志和运行时 GIL 状态，普通解释器或启用了 GIL 的
运行方式会导致配置失败。Python 源码仍保留 3.9+ 兼容性，开发与 CI 统一使用 3.14t。完整检查为：

```sh
meson test -C builddir --print-errorlogs
```

Ruff 0.16.9 检查及格式化全部 Python 文件，覆盖 `源码/`、`测试/`、`基准/`
与产品图标生成脚本。运行 `meson compile -C builddir 格式化` 应用格式化；
`lint` 及完整检查要求 `ruff check .` 和 `ruff format --check .` 均通过。
规则检查基础语法、未使用名称和导入顺序，目标版本为 Python 3.9；固定 Ruff 版本
以保持本地与 CI 的格式一致，不排除图标生成器等项目自有代码。

类型检查使用 ty 与 tsc，缺少 Ruff、ty、tsc 或 Node.js 时完整检查直接失败，不再使用
`ADWCODE_TYPECHECK_STRICT` 开关。ty 配置见 `ty.toml`，按 Python 3.9 解析，
将全部诊断设为错误；这不等同于 mypy 的原有严格模式。Meson 的完整检查同时
执行类型检查，避免离线扩展测试因缺少 Node.js 被跳过而未被发现。

`meson compile -C builddir 校验` 校验主题及产品图标的注册和文件完整性、十六进制
颜色、键覆盖与对比度，缺少产物时失败；它不负责证明产物与生成器逐字节一致。生成后核对 Git 差异；
CI 的生成校验要求重新构建后 `主题/` 和 `package.json` 不产生额外差异。
发布工作流构建固定蓝色的 6 个主题变体，核对产物与提交一致，通过完整检查后打包。

缺少随附颜色键表时，主题校验直接失败。CSS 校验找不到已安装的样式表时也会
失败，可用 `python3.14t 源码/检查样式.py --样式表 /路径/workbench.desktop.main.css`
指定构建。完整离线检查在未安装 VS Code 时跳过类名对照；跳过不代表界面已验证。
刷新默认数据时，所有下载与解析成功后才写入四个数据文件，下载失败保留原数据。

## 性能测量

按任务需要运行 `meson compile -C builddir 性能基准`，在临时副本中测量生成、
校验与打包，并运行模拟宿主下的扩展逻辑基准。结果保存为
`builddir/performance.json`，不覆盖仓库的主题或 VSIX。

真实工作台的 CSS 对比使用 `基准/工作台基准.py`，需要独立安装的 Playwright；
它创建专用窗口与临时配置，结束后关闭，不重载工作窗口。
运行方式见源码仓库的 `基准/README.md`，本机方法、结果与原始样本见
[性能测试](07-性能测试.md)。性能测试不在常规检查中自动运行，也不设跨机器耗时门槛。

## 手动预览

1. 配色源码有变化时先 `meson compile -C builddir 主题`。
2. 如果用 VSIX 安装扩展，先打包并直接安装即可更新，无需卸载旧版或额外升级步骤；
   详见 [中文接口迁移](08-中文接口迁移.md)。符号链接开发安装直接读取仓库。
3. 执行“AdwCode: 安装 GNOME 外观（CSS）”，更新副本与加载配置。
4. 保存工作后执行加载器的“Reload Custom CSS and JS”并重载窗口。
5. 检查浅色、深色、高对比度、键盘焦点、菜单及子菜单、横纵滚动条、缩放与窄窗。

首次尚未启用加载器时，应使用其“Enable Custom CSS and JS”。VS Code 升级后
需要重新应用补丁。命令沿用加载器实际显示名称，不把外部命令自行改名。

记录验证边界：静态检查、单个界面的人工确认和完整截图回归，三者
含义不同。避免用旧截图或单个界面作为全部外观已验证的依据。

## 提交与发布

VSIX 产物不变的改动只提交与推送，不更新发布版本号、不打版本标签、不创建 Release。
是否发布以实际打包内容的变化为依据，不因产生新提交而自动发布。

1. 明确本次提交范围，按路径暂存，排除调试日志、构建产物及无关改动。检查暂存差异及 `git diff --cached --check`。
2. 使用 [贡献规范](../CONTRIBUTING.md) 的中文类型前缀，描述最终实际行为。
   正文可列修改原因与验证结果，避免只有“准备发布”等过程性描述。
3. 本机 Git 身份缺失时核对 gh 账号和已有作者信息；必要时询问，不伪造邮箱。
   临时身份可通过 `git -c user.name=… -c user.email=… commit` 指定。
4. 版本只修改 `package.json`；提交后通过 `源码/生成变更日志.py` 从 Git 历史生成日志，
   不手工维护版本章节。更新版本不等于
   已公开发布，提交也不等于已推送。
5. 打包检查 VSIX 的版本、主题清单和归档完整性；`[Content_Types].xml` 中的
   扩展名不带前导点，CSS 类型为 `text/css`。VSIX 不提交到仓库。
6. 确认发布范围与权限后推送对应 `v<版本>` 标签，触发发布工作流。市场发布需要
   `VSCE_PAT`、`OVSX_PAT`，缺失时工作流跳过对应市场，不宣称市场已经发布。
   同一引用的发布任务串行执行；重跑时保留已有 Release 和同名 VSIX，只补齐缺失附件
   并更新说明，市场发布复用已公开的 VSIX。不要移动已发布的版本标签；确需修正
   附件时，应单独确认替换范围。

文档记录稳定流程；提交状态、环境配置和发布结果以实际检查为准。
公共文档中的相对链接必须指向随仓库提交的文件。

## 自动变更日志

仓库不维护手写的 `CHANGELOG.md`。完整 Git 历史、提交标题与版本标签是唯一输入；
已发布记录见 [GitHub 发布页](https://github.com/KOTONEX/AdwCode/releases)。

```sh
meson compile -C builddir 变更日志
meson compile -C builddir 发布说明
```

第一条生成 `builddir/CHANGELOG.md`，第二条生成 `builddir/release-notes.md`。
两者均是忽略的构建产物，不入库。脚本也可通过 `--输出` 指定输出位置。
提交标题按 `新增`、`修复`、`文档`、`测试`、`重构`、`杂务`、`初始化` 分组，
未分类的旧标题归入“其他”。日志不包含提交正文和未提交修改；正式记录需要先提交。

主线可达的 `v<版本>` 标签作为发布边界，按主线提交顺序排列；版本日期使用标签
所指提交的日期。每个范围包含合入主线的非合并提交，合并提交自身不重复列出。
不在当前主线上的标签不参与划分，首个版本包含此前全部提交，最近标签之后的
提交归入“未发布”。同一提交有多个版本标签时失败，避免发布范围产生歧义。

发布工作流执行 `源码/生成变更日志.py 发布说明 --标签 "$GITHUB_REF_NAME"`，必须同时
满足标签存在、指向 HEAD 且与 `package.json` 版本一致。无标签的本地说明明确标为
预览，不能作为发布校验通过的证据。浅克隆会失败；克隆时获取完整历史和标签，
CI 与发布使用 `fetch-depth: 0`，不在检查时自动访问网络补齐历史。

普通打包自动从 Git 生成 `扩展/CHANGELOG.md` 并写入 VSIX，无需先运行日志
目标。无 Git 的源码导出副本须显式传入先前生成的日志：

```sh
python3.14t 源码/打包扩展.py --变更日志 /路径/CHANGELOG.md
```

性能基准在计时前生成固定日志，临时源码副本的打包使用该日志，不复制 Git 仓库，
也不把生成历史日志的耗时计入 VSIX 打包测量。

## 更新项目说明

功能行为变化时同步相关文档：架构说明记录已实现行为，待办记录剩余范围，
提交标题记录具体变化，由自动日志汇总；AGENTS.md 只保留稳定约束和入口。不要复制多份完整
实现说明，也不要把“计划做”写成“已经完成”。
